# portfolio

Персональный сайт-портфолио DevOps-инженера. Чистые HTML/CSS/JS без сборки,
без фреймворков и без обязательных платных сервисов.

**Текущий этап: публичный preview с черновым контентом.** Основным выбран
зелёный дизайн в стиле раннего Steam / CS 1.6. GitHub Pages автоматически
обновляется после успешного CI для push в `main`. Пока placeholders не заменены,
страница закрыта от индексации поисковиками.

**Стоимость размещения: $0/месяц** (GitHub Pages + уже оплаченный домен).

---

## Быстрый старт

```bash
git clone https://github.com/inemkovich/portfolio.git
cd portfolio
python3 -m http.server 8080 --directory docs
# открыть http://localhost:8080
```

Или через Docker (опционально, если хотите окружение ближе к продакшену):

```bash
docker compose -f docker/docker-compose.yml up --build
# открыть http://localhost:8080
```

## Почему такой стек

| Решение | Причина |
|---|---|
| HTML/CSS/JS без сборки | Ноль зависимостей, ноль build-шагов, ничего не устаревает и не ломается через год |
| GitHub Pages как хостинг | $0 навсегда, автоматический HTTPS, нативная интеграция с GitHub Actions |
| Terraform для DO — опционально | Демонстрация IaC-навыков + запасной вариант хостинга в вашем DO-аккаунте |

## План реализации

- [x] **Этап 0 — Скелет проекта.** Структура репозитория, конфиги для
      агентов (`CLAUDE.md`, `AGENTS.md`), CI/CD-пайплайны, дизайн-система
      и вёрстка одностраничника с placeholder-контентом. *(готово в этой
      поставке)*
- [ ] **Этап 1 — Контент.** Замените все `[плейсхолдеры]` и `TODO:` в
      `docs/index.html` реальными данными. Ориентируйтесь на
      `content/CONTENT_GUIDE.md`. Добавьте резюме в
      `docs/assets/resume.pdf`, реальные ссылки на GitHub/LinkedIn, email.
- [ ] **Этап 2 — Публикация preview.** Репозиторий уже публичный, Pages использует
      GitHub Actions, автоматический деплой после успешного CI настроен.
      Осталось отправить подготовленные коммиты в `main` и проверить workflow
      `CI Checks`, затем `Deploy to GitHub Pages` во вкладке Actions.
- [ ] **Этап 3 — Домен.**
      1. Добавьте домен в Settings → Pages → Custom domain.
      2. После этого у регистратора добавьте DNS-записи для GitHub Pages:
         - Для apex-домена (`example.com`): 4 A-записи на
           `185.199.108.153`, `185.199.109.153`, `185.199.110.153`,
           `185.199.111.153`.
         - Для поддомена (`www` или `portfolio.example.com`): CNAME на
           `inemkovich.github.io`.
      3. Дождитесь применения DNS и автоматической выдачи HTTPS-сертификата.
- [ ] **Этап 4 — Полировка.**
      - После заполнения контента снимите `noindex`, разрешите индексацию
        в `robots.txt` и добавьте `sitemap.xml` с итоговым доменом.
      - После подключения своего домена обновите `og:url` в `index.html`.
      - Прогоните [PageSpeed Insights](https://pagespeed.web.dev/) /
        Lighthouse — для чистого HTML/CSS без фреймворков обычно сразу
        99-100 по производительности.
      - Проверьте доступность (контраст, alt-тексты, навигация с
        клавиатуры).
- [ ] **Этап 5 — Опционально.**
      - Разверните альтернативный хостинг на DO App Platform через
        `infra/` (см. `infra/README.md`) — если хотите иметь запасной
        вариант или пример IaC в портфолио.
      - Добавьте приватную, не требующую cookie-баннера аналитику, если
        хочется видеть посещаемость — например самостоятельно
        развёрнутый [GoatCounter](https://www.goatcounter.com/) (есть
        бесплатный публичный инстанс для некоммерческого использования)
        или [Cloudflare Web Analytics](https://www.cloudflare.com/web-analytics/)
        (бесплатно, без необходимости проксировать домен через Cloudflare).
        Проверьте актуальные условия перед подключением — политики
        бесплатных лимитов у сторонних сервисов могут меняться.
      - Заведите короткий тех-блог как ещё один раздел (`docs/blog/`) —
        частый способ для DevOps-инженеров показать глубину экспертизы.

## Обслуживание

Проект не требует регулярного обслуживания — нет зависимостей, которые
устаревают, нет сервера, который нужно патчить. Раз в несколько месяцев
имеет смысл:
- Обновить даты/достижения в разделе Experience.
- Добавить новый проект, если появился достойный кейс.
- Проверить, что workflow `ci.yml` всё ещё проходит (GitHub иногда меняет
  версии Actions).
